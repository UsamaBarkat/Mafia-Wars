# tasks-2c.md — Mafia Wars · Phase 2 Slice 2c Task Breakdown

Build order for Slice 2c (Mafia private chat, Day voting chat, Play Again). Derived from [../CLAUDE.md](../CLAUDE.md) and [spec-2c.md](spec-2c.md). Each task is sized to finish and verify in one sitting. Build one, stop for review, then the next — never sprint the whole list (CLAUDE.md).

Backend (unchanged): **Firebase, Spark/free, no Cloud Functions; RTDB; Anonymous Auth.** Both new chats extend 2a's existing chat mechanism (same `ChatMessage` shape, same append-only pattern) rather than reinventing it. Play Again is a room-lifecycle reset, living alongside `startGame.ts`/`dealRoles.ts`/`endRoom.ts` in `lib/room/`, not the night/day resolver logic in `lib/game/`.

Convention per task: **Goal**, **Files**, **Satisfies**, **Done when**, **Depends on**.

> **Security Rules land before any UI that relies on them (task 2)**, and both pieces of data-layer logic (the generalized chat mechanism, task 3; the Play Again reset, task 4) land **before the UI that uses them** — same discipline as 2a/2b.

## 2. Security Rules — Mafia-chat/Day-chat scoping + Play Again's moderator write grants — ✅ done

- **Goal:** Every Security Rules change this slice needs, written and emulator-verified **before any UI is built against them.**
- **Files:** `database.rules.json`.
- **Satisfies:** spec-2c FR‑1–FR‑10 (chat access), FR‑12/15/16 (Play Again's reset), Backend mechanism notes.
- **Done when**, precisely:
  - **`mafiaChat` (new node):** parent `.read` — `auth != null && privateRoles/{auth.uid}/role === 'Mafia' && players/{auth.uid}/alive === true` (membership via `privateRoles`, **not** `mafiaTeam` existence — D4/solo-Mafia gotcha). Parent `.write` — moderator only (bulk clear for Play Again; **no** per-Mafia parent write). Child `$msgId.write` — `!data.exists() && newData.uid === auth.uid && privateRoles/{auth.uid}/role === 'Mafia' && players/{auth.uid}/alive === true && game/phase === 'night'` (write is phase-gated, D6; read is not). `.validate` identical shape/caps to 2a's `chat/$msgId`. **No moderator read grant anywhere on this node** (D2).
  - **`dayChat` (new node):** parent `.read` — `auth != null && (players/{auth.uid}.exists() || moderatorId === auth.uid)` (any room member, matching `chat`'s existing read rule — D1). Parent `.write` — moderator only (bulk clear). Child `$msgId.write` — `!data.exists() && newData.uid === auth.uid && players/{auth.uid}/alive === true && game/phase === 'day'` (living players only; the moderator's read access does **not** include a posting path in the intended design — see the note below on the accepted limit of this guarantee). `.validate` identical shape/caps to 2a's `chat/$msgId`.
  - **`chat` (existing 2a node) — one addition only:** add a parent `.write` grant for the moderator (bulk clear for Play Again). **Do not touch** the existing `.read` rule or the existing `$msgId.write`/`.validate` rules — 2a's lobby chat keeps working exactly as it does today for everyone else.
  - **`rounds` (existing 2b node) — one addition only:** add a parent `.write` grant for the moderator (bulk clear of every round's `nightActions`/`nightResults`/`nightOutcome`/`votes`/`dayOutcome` in one shot). **Do not touch** any existing nested per-child rule (`nightActions/$uid`, `votes/$uid`, etc.) — players still write only their own entries via the rules that already work; this only adds an additional, broader grant, it doesn't replace the narrower ones.
  - **`players/{uid}/viewed` (existing 2a/2b field) — one addition only:** currently writable only by that player themselves (via the parent `$uid`'s `auth.uid === $uid` rule — same as `name`/`connected`). Add a **moderator** `.write` grant at `viewed` specifically (mirroring how `alive` already has its own child rule), so Play Again can reset it for every player. Unlike `alive`, **do not** restrict the existing player self-write — both the player (marking their own role viewed) and the moderator (resetting everyone's) need to keep working.
  - **Documented, accepted limit (not a bug to fix):** granting the moderator parent-level write on `rounds`/`chat`/`mafiaChat`/`dayChat` for bulk-clear also technically permits them to write individual entries within those nodes (RTDB has no "delete-only" primitive) — e.g. the moderator could, via direct database access, post into Day chat even though the UI never gives them a text box for it. This is the same "secret enough for friends, not bulletproof" trust boundary spec-2b already accepts for the resolver; it is not a new gap introduced by this task, and is not something to design around.
  - **Emulator-verified** with real signed-in identities (mirroring the verification style of every 2b rules task): a living Mafia can read+write `mafiaChat`; a living Doctor/Detective/Civilian is denied reading it; a solo Mafia (no `mafiaTeam` entry) still has full access; a Mafia who is set `alive:false` is immediately denied both read and write; a living player can read+write `dayChat` only while `game.phase==='day'`; an eliminated player can read `dayChat` but is denied writing it; the moderator can read `dayChat` and is denied writing it via the **intended UI path** (no post button) while the documented raw-access limit above is understood, not "fixed"; the moderator can bulk-clear `rounds`/`chat`/`mafiaChat`/`dayChat`/`viewed` while a non-moderator is denied doing the same.
  - `tsc` clean (JSON validity); no app code yet.
- **Depends on:** 1
